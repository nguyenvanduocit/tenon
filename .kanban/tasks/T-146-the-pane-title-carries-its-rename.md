# T-146: The pane title carries its own rename

> Renaming a pane happens in the pane's own header — no window-wide modal for either the
> manual edit or the AI generation.

- **priority**: high
- **effort**: M

## Why

`PaneRenameOverlay` dims the whole shell and traps focus to show a spinner the pane already
has room for. For AI Rename that modal carries no controls the pane needs — the operator
asked for the generating/failed state to live on the pane title instead. For manual Rename
the modal exists only to host one text field, which the title itself can be.

Two operator decisions, taken 2026-08-14 before the first edit:

1. **Failure**: the title shows `Rename failed` for a few seconds with the provider's message
   as its tooltip, then returns to the automatic title on its own. Retry is the menu item.
2. **Manual rename**: edited inline on the title. `PaneRenameOverlay` is deleted outright,
   not kept for the manual branch.

## Criteria

- [x] AI Rename presents no modal: the pane's own title reads `Naming…` while the bounded
      Companion task runs, and the pane keeps working under it.
- [x] A generated title lands through the same `WorkspaceStore.renameSlot` mutation; the
      title returns to normal presentation with no further state.
- [x] A failed generation shows `Rename failed` on the title with the message as tooltip and
      clears itself after a bounded linger; the pane's automatic title returns.
- [x] Manual Rename edits the title in place — Enter commits through `renameSlot`, Escape
      restores, an emptied field restores the automatic content title.
- [x] Two panes can generate at once; each one's state belongs to its own pane, and losing a
      pane cancels only that pane's task (`retainOnly` still the one teardown authority).
- [x] `PaneRenameOverlay` no longer exists and nothing mounts a rename modal.
- [x] `WS-FR-028`/`WS-FR-029` restated in `workspace-shell.prd.md` with scenarios in
      `workspace-shell.feature`; decision rows record both operator choices.

## What shipped

`PaneRenameOverlay` is gone. `PaneRenameCoordinator` holds `phases: [UUID: PaneRenamePhase]`
instead of one window-level `presentation`, which is what makes two panes able to name
themselves at once; `retainOnly` stays the single teardown authority and now cancels only the
panes that died. `PaneRenameChrome` is the pure value deciding what the title says in each
phase, so the words are asserted without a window and `SpatialSlotCardView` only paints them.
The card's title field becomes editable in place — Return commits, Escape restores, clicking
away commits — and the field's rect is exempt from pane-drag surface in `hitTest`,
`mouseDown` and `menu(for:)`, the same rule every other header control gets.

Two things the tests could not settle:

- **The glyph.** The first form used `⟳` for generating. `TENON_PANE_RENAME_SNAPSHOT` showed
  it as an unreadable smudge at the glyph column's 9 points while `Naming…` beside it was
  perfectly legible, so a generating pane keeps its content glyph and carries the state in
  amber instead. Failure keeps `!` in red, which reads.
- **No spinner.** An animated glyph writes `stringValue` at 10 Hz, and each write invalidates
  an `NSTextField`'s intrinsic size and re-solves the header strip on the main thread — the
  churn T-091 and T-141 exist for. Recorded as a decision row, not left implicit.
