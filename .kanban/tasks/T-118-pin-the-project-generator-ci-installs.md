# T-118: Pin the project generator CI installs

> `brew install xcodegen` takes whatever version Homebrew ships that day. It shipped 2.46.0,
> which orders targets differently from the 2.45.4 that generated the committed project, so
> `git diff --exit-code -- Tenon.xcodeproj` fails on a tree nobody changed.

- **priority**: high
- **effort**: S
- **prd**: TENON-PRD-015 (ENQ-FR-040, ENQ-NFR-012)

## Measured

Run `31416924458` cleared the terminfo failure T-117 fixed and stopped one step later, in
*Verify generated Xcode project is current*. The diff is not a source change — it is the
same project described in a different order, plus an `Embed Frameworks` phase:

```
-  634FB0FDB8CEFE2B63C94CD6 /* Tenon */,
+  C63EECBA60675E817F296453 /* TenonIntentCore */,
+  37FFD0A1E219363513112C50 /* Embed Frameworks */,
```

The cause is stated in the generator's own release notes for 2.46.0:

> Targets in the generated project now follow the declaration order from the source spec.
> Previously they were always sorted alphabetically.

Locally `xcodegen --version` is **2.45.4**; the runner poured **2.46.0**
(`Pouring xcodegen--2.46.0.arm64_sequoia.bottle.1.tar.gz`). Same spec, two generators, two
projects — and `xcodegen generate && git diff --exit-code` on this machine passes, which is
exactly what makes the failure invisible from here.

## Why this is the same defect T-117 fixed

Both are build inputs that come from whatever the machine happens to have rather than from
something pinned. `setup-ghosttykit.sh` already shows the shape the answer takes here:
a pinned tag, a recorded SHA-256, and a verification step that fails loudly. `brew install`
has none of those. ENQ-FR-040 was written for this class and covers it.

Note `release.yml` does **not** run the project-is-current check, so this blocks CI going
green, not cutting a release.

## Which version to pin, decided on evidence

The obvious move was to take 2.46.0, since it is newer and the runner already had it. That
was tried and rejected. Generating with it produces a 21-line diff, and only part of it is
the harmless reordering:

```
+ 37FFD0A1E219363513112C50 /* Embed Frameworks */ = {
+     files = ( … TenonIntentCore.framework in Embed Frameworks … );
```

Nothing in the app loads that framework. `otool -L` on the shipped 0.1.0 binary and on
`TenonCore.framework` names `TenonCore`, `OrderedCollections` and `JSONSchema` and nothing
else, and `Contents/Frameworks/` holds exactly those three — `TenonIntentCore` is linked
statically. Taking 2.46.0 would ship a fourth framework nobody loads, add one more thing to
sign, and make the artifact differ from the one Apple notarized.

So the pin is **2.45.4**: the generator that produced the shipped 0.1.0, verified end to
end. The defect was never "the version is old", it was "the version is whatever the machine
happened to have". Upgrading is a separate change, gated on a build that runs.

## Criteria

- [x] CI installs one pinned generator version with a verified checksum rather than `brew
      install <name>`
- [x] The committed `Tenon.xcodeproj` is generated by that same pinned version
- [x] `docs/development.md` names the version a contributor needs, so a local generate does
      not silently disagree with CI
- [ ] A CI run passes *Verify generated Xcode project is current* on an unchanged tree

## Evidence

The whole CI sequence, replayed locally from a tree with `.build/tools` deleted: the script
downloads 2.45.4, matches its recorded SHA-256, installs it, and then
`xcodegen generate && git diff --exit-code -- Tenon.xcodeproj` passes — the exact step that
had failed on every run since 2026-08-07. `swift build` is clean afterwards.

`scripts/test-setup-xcodegen.sh` asserts the pin against the digest GitHub publishes for
that tag, so a version bumped without its checksum fails rather than installing something
unexamined. Mutation-checked: zeroing `ARCHIVE_SHA256` turns it red naming both digests,
and restoring it turns it green.

Two smaller things the change had to get right. The staging directory is cleaned by a trap
that expands its path at registration, because a `local` variable is out of scope by the
time an EXIT trap runs — the first version of the script failed on its second run with
`staging: unbound variable`. And `prune-build-cache.sh` keeps `tools`, since it is a
verified build input rather than a cache, and dropping it costs a download on the next
build.
